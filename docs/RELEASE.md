# Release Process

TailRef ships through **GitHub Releases** and updates itself with
`electron-updater` inside the NSIS-installed application. The portable `.exe`
stays a manual download.

The pipeline is tag-driven: pushing a version tag builds, tests, verifies and
publishes the release. A broken build never becomes a release.

> This document covers versioning and the Windows update channel. For the
> current cross-platform pipeline (separate Windows and Linux jobs, checksums,
> release notes, manual test builds), see
> [`RELEASE_PROCESS.md`](RELEASE_PROCESS.md). For Linux builds, see
> [`LINUX_BUILD.md`](LINUX_BUILD.md).

## Versioning

TailRef follows [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.

| Change | Version bump | Example |
|---|---|---|
| Bug fixes, docs, small internal cleanup | PATCH | `1.4.1 → 1.4.2` |
| New features, backwards compatible | MINOR | `1.4.2 → 1.5.0` |
| Breaking changes to files, settings or APIs | MAJOR | `1.5.0 → 2.0.0` |

Rules:

- `package.json` is the **single source of truth** for the version.
- The Git tag must be `v` + the exact `package.json` version (`v1.4.3`).
- `CHANGELOG.md` must have a matching section.
- `dist/latest.yml` is generated by `electron-builder`; its `version` field must
  match the tag. The workflow refuses to publish otherwise.
- Never reuse or overwrite a published version or tag.
- Never rewrite published Git history.

## How automatic updates work

| Piece | Behaviour |
|---|---|
| Check on startup | 25 seconds after the window opens, never blocking startup |
| Periodic checks | Every 4 hours while the app is running |
| Manual check | Settings → About → **Check for updates** |
| Preference | Settings → About → **Automatic update checks** (on by default) |
| Download | Only after the user presses **Download update** |
| Install | Only after a verified download and a save handshake |
| Stable channel | `allowPrerelease = false`, `allowDowngrade = false` |
| Portable build | No in-place update; **Open download page** is shown instead |
| Development run | No update checks; the About page explains why |
| Offline / errors | Friendly message, exponential backoff (30 min → 1 h → 4 h) |

The main process owns the entire update lifecycle. The renderer only receives a
small read-only state object and can request check / download / install. It has
no access to Node, the filesystem or the updater object.

Before installing, TailRef asks the renderer to save:

- **Auto save mode:** the current board is flushed to disk.
- **Manual save mode:** if the board changed since the last `.tail` save, the
  user chooses **Save and restart**, **Restart without saving** or **Cancel**.
- If saving fails or the renderer does not answer, installation is postponed.
  The window is never force-closed.

## Release pipeline

`.github/workflows/release.yml` runs when a tag matching `v*.*.*` is pushed, or
when a maintainer starts it manually with an existing tag.

The workflow is split into `prepare`, `test`, `windows`, `linux` and `release`
jobs. Windows and Linux are built on separate runners, every artifact is
verified, `SHA256SUMS.txt` and the release notes are generated, and only then is
the GitHub Release created. A failed job means no release.

The full job graph, artifact names, manual test builds and rollback steps are in
[`RELEASE_PROCESS.md`](RELEASE_PROCESS.md). In short:

1. `prepare` validates the tag format, the `package.json` version and the
   matching `CHANGELOG.md` section.
2. `test` runs the pure gates, the production dependency audit and the Linux
   native build.
3. `windows` runs the application suites and builds NSIS + portable.
4. `linux` builds the AppImage, deb and rpm, inspects their contents, installs
   and removes the deb, and smoke-launches the AppImage under Xvfb.
5. `release` writes the checksums, generates the release notes, creates the
   GitHub Release and re-verifies every asset.

`latest-linux.yml` is produced by electron-builder but is never uploaded: Linux
has no in-app updater.

### Test build before the public release

A GitHub Release cannot be private inside a public repository, so a manual run
uploads a **draft** instead (`publish: true`, `draft: true`). A draft is not
listed on the Releases page and anonymous users cannot download its assets; you
can download the AppImage, deb and rpm and test them on a real Linux machine.
Pressing **Publish release** later keeps the same tag and assets. Because a
draft is not a published release, Windows installations do not receive it
through the in-app updater.

### Stable releases

A tag without a suffix is stable:

```bash
git tag -a v1.4.3 -m "TailRef 1.4.3"
git push origin v1.4.3
```

The release is marked **latest** and becomes the target of
`https://github.com/Roxsmb/tailref/releases/latest`, which is what
`electron-updater` reads for stable installations.

### Prereleases

A tag with a suffix is a prerelease:

```bash
git tag -a v1.5.0-beta.1 -m "TailRef 1.5.0 beta 1"
git push origin v1.5.0-beta.1
```

It is published with the **prerelease** flag, so GitHub's `releases/latest`
endpoint ignores it. Stable installations therefore never receive it. Only a
user who enables the beta channel can see prereleases.

## Local dry run

Build and inspect the exact artifacts without publishing:

```powershell
node scripts/build-app.js
npm run gates
npm test
npx electron-builder --win nsis portable --publish never
node scripts/verify-package.js
```

Check the generated files:

```powershell
Get-Content .\dist\latest.yml
Get-Content .\dist\win-unpacked\resources\app-update.yml
Get-FileHash .\dist\TailRef_Studio.exe -Algorithm SHA256
Get-FileHash .\dist\TailRef_Studio_Setup.exe -Algorithm SHA256
```

Launch `dist\win-unpacked\TailRef Studio.exe` and confirm Settings → About shows
the current version and the update panel. A development run (`npm start`) must
show the development explanation instead of checking GitHub.

## Testing the real update lifecycle

Compilation alone does not prove that updates work. Before a public stable
release:

1. Publish a prerelease build (`vX.Y.Z-beta.N`) or keep the previous stable
   release installed.
2. Install the **older** NSIS build on a clean Windows user profile.
3. Create a board, switch to manual save mode, and leave an unsaved change.
4. Publish the newer stable build.
5. Open the older installation and wait for the startup check (or press
   **Check for updates**).
6. Confirm: update available → download → **Restart and install** → the save
   dialog appears for unsaved manual work → the app restarts into the new
   version.
7. Confirm that boards, images, preferences, layouts and `.tail` files are
   intact.
8. Repeat with the portable build and confirm it offers **Open download page**
   instead of installing.

## Verification after publishing

- [ ] `https://github.com/Roxsmb/tailref/releases/latest` points at the intended
      stable release.
- [ ] The release contains `TailRef_Studio_Setup.exe`,
      `TailRef_Studio_Setup.exe.blockmap`, `TailRef_Studio.exe`, `latest.yml`,
      `TailRef-X.Y.Z.AppImage`, `tailref_X.Y.Z_amd64.deb`,
      `tailref-X.Y.Z.x86_64.rpm` and `SHA256SUMS.txt`.
- [ ] `latest-linux.yml` is **absent**: Linux has no in-app updater.
- [ ] `latest.yml` references `TailRef_Studio_Setup.exe` and the correct
      version.
- [ ] Re-download the assets and compare their SHA-256 hashes.
- [ ] The release notes render correctly and state the license
      (GPL-3.0-or-later).
- [ ] The matching Git tag is pushed, so the Corresponding Source required by
      GPLv3 section 6 is downloadable.
- [ ] An older installed build can update to the new release.

## Rollback

If a release is broken:

1. Do **not** delete the release or the tag.
2. Mark the release as broken in its notes.
3. Publish a fixed PATCH release; `electron-updater` only moves forward.
4. If the build is unsafe to run, edit the release notes to say so clearly and
   point users to the last good version.
5. If the release was accidentally marked **latest**, correct the flag on
   GitHub so stable installations stop seeing it.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| “No published update was found” | No release, or `latest.yml` missing | Check the release assets and `latest.yml` |
| “GitHub is temporarily limiting” | Unauthenticated API rate limit | Wait; automatic checks back off |
| “Could not reach GitHub” | Offline, proxy or firewall | Check the connection; retry manually |
| “Downloaded update could not be verified” | Corrupt or mismatched blockmap | Re-publish the release assets |
| Update panel is disabled | Development run or portable build | Use the NSIS-installed build |
| Install does not start | Blocked execution policy / antivirus | Download the installer from GitHub |
| Workflow cannot push `.github/workflows` | Token lacks the `workflow` scope | Use a token with `repo` + `workflow` |

## Security notes

- Update decisions run in the main process; the renderer cannot start a
  download or an install on its own.
- Every update IPC handler verifies that the sender is the main TailRef window.
- Release notes and version metadata are sanitised before they reach the UI.
- Downloads are opt-in, installation requires a completed download, and user
  data is saved first.
- No publishing credentials are stored in the application or the repository;
  the workflow uses the short-lived `GITHUB_TOKEN`.
